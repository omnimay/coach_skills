# 下发工作流详解

## 0. 适用性判定 + 报告结构化提取

### 适用性（入口泛化）

入口不限于录音分析：**任意分析报告、总结、复盘、能力评估文档**都可能触发本技能。判定标准只有一条——报告须同时含两类信息：

- 「人」：学员姓名或工号
- 「短板」：不足/待改进/弱项/建议提升类结论

缺任一（如纯知识文档、无人员评估的会议纪要）→ **不强行提取**，如实告知不适用，可建议人工梳理出「人员+短板」清单后再来。

### 提取

- 输入：用户提供的报告（文档、文本或粘贴内容）。字段不全不阻塞：缺工号可按姓名找人，缺姓名按工号解析，两者都缺的学员列出请用户补充
- 提取目标 schema（宿主 LLM 结构化输出）：

```json
{
  "students": [
    {"name": "张三", "employee_no": "E1001", "weaknesses": ["价格异议处理不足", "产品参数不熟"]}
  ],
  "report_meta": {"source": "雍禾_录音分析报告_20260923"}
}
```

- 规则：
  - 短板按语义聚类，同义合并（"报价应对弱" ≈ "价格异议处理不足" → 一条）
  - **0 学员或 0 短板 → 终止并告知**，不猜不建
  - 同工号重复学员 → 合并一人，短板取并集
  - 不虚构不脑补字段；报告没写的留空走补全路径，不编

## 1. 标签对齐

1. `training.course.label_list` 拉本组织全量标签词表（可选 `keyword` 过滤）
2. 映射规则：短板语义 ↔ 标签名（精确或近义）；一个学员多短板 → 多标签；多学员同短板 → 同一标签
3. 映射不上的短板：暂记为"待建标签"，**不阻塞匹配**；建课打标时以 `id=0` 新建补齐

## 2. 课程匹配（AND 语义 + HITL）

- `training.course.list` 传 `labelIds`：**AND 语义**——课程必须同时具备全部传入标签（后端 `HAVING COUNT(DISTINCT label_id) = ?`）。不传 `labelIds` 的 course.list 是全量列表，不用于匹配
- 命中判定：
  - 命中 1 门 → 进入确认门
  - 命中多门 → HITL：列候选（课程名 + 各自标签），**默认推荐标签数与学员标签集最接近的**，让用户挑
  - 未命中 → 建课（下一节），**不要放宽标签重试凑命中**，也不要拿名字相似的课充数
- 多学员场景：逐学员（或按相同短板分组）各自匹配；不同学员可命中不同课程

## 3. 建课委托（未命中才走）

- **委托方式**：按 `ai-customer-design` 技能的 §建课工作流 执行（异步工具集 `training.ai_customer.create / update / update_status / get`）
- 课程简报构造：报告里的短板结论 = 评估维度输入；场景与 AI 角色按报告业务背景补全；六要素检查清单见 ai-customer-design §课程简报检查清单
- 继承红线（详见该技能，此处仅提示）：
  - `ai_customer.update` 秒返 taskId 即发送成功，**不重复提交**
  - 完成判定唯一权威：`ai_customer.get` 返回 `create_status_created` 且 `stages` 非空；不信 AI 回复文字
  - 并发建课 ≤3
- 报告原文要作为课程参考资料时，走 ai-customer-design 的文档上传路径（`file.upload_document` + `metadata.fileIds`），不要把报告改写成纯文字传 message
- **新课未就绪（get 验证未过）→ 不进入下发段**：告知用户课程生成中，待就绪后再继续下发步骤

## 4. 打标回写（闭环的必要步骤）

`training.course.label_batch_create`：

```json
{"course_id": 123, "labels": [
  {"id": 7,  "name": "异议处理"},
  {"id": 0,  "name": "竞品对比应答"}
]}
```

- `id=0` → 新建标签，落库标记 AI 生成（后台人工审核可辨识）；`id≠0` → 关联现有标签
- ⚠️ **整体替换语义**：该调用会替换该课程的全部标签关联。每次必须传**全集** = 应保留的现有标签（先 `label_list` 传 `courseId` 查出）+ 本次新增；只传新增会把原有标签清掉
- 响应：`createdLabels` 为本次实际新建的标签，`success:true` 为成功
- **不打标的后果**：新课对标签匹配永远隐形 → 下次同类短板匹配不到，又建一门重复课，闭环断裂。新建课程后打标不是可选项

## 5. 确认门（先问再发）

- 时点：分析 + 匹配（含建课打标）完成、向用户汇报之后；任何 `create_open_project` 调用之前
- 汇报内容：学员清单（姓名/工号）、各自短板、匹配或新建的课程
- 询问话术示例："是否为以上 N 位学员下发培训任务？（可以发，也可以先不发）"
- **等待明确答复**：用户说发 → 继续；说不发/沉默/转移话题 → 不创建、不追问，分析结果即本次交付
- 名单含未命中工号时如实列出，只对命中学员执行

## 6. 找人路径（名单 → user_id）

| 用户提供了 | 路径 |
|---|---|
| user_id | 直接用 |
| 工号 | `organization.user.batch_resolve`（`{"employeeNos":["E1001"]}`，≤50、去重保序）→ `results:[{employeeNo, isSuccess, userId, failedReason}]` |
| 仅姓名 | `training.organization.tree` 按姓名找（下） |

**organization.tree 按姓名找人**：

- 入参 `treeId`（0 = 全部顶级部门）+ `size`（默认给 9999）；`includesDeletedMembers` 保持默认 false（离职用户会被下发端防线拒绝，别送）
- 顶级返回部门节点；要传**成员所在部门的 treeId** 才返回成员——先 `treeId=0` 拿部门列表按名称初筛，再展开对应部门；不确定就逐部门展开
- 成员在 `children` 数组：`name`（姓名）、`id`、`isActive`、`isEnable`
- **成员 `id` 格式 `<部门id>_<user_id>`，下划线后段即可直接传 `userIds` 的裸 user_id**（实证："5_5" → uid 5）
- 按 `name` 精确匹配；优先 `isActive=1`；重名/多候选 → 列出（姓名+部门）让用户选，不要猜
- 组织树确实找不到 → 如实报告，请用户提供工号或核对姓名；**禁止虚构 user_id**
- `batch_resolve` 全部未命中 → 终止不下发；部分未命中 → 只下发命中的，未命中的进人工清单交用户

## 7. 下发契约（training.task.create_open_project 成员任务）

| 参数 | 必填 | 说明 |
|---|---|---|
| `courseId` | 是 | 课程 ID |
| `name` | 否 | 任务名，默认课程名 |
| `userIds` | 否 | 学员 user_id 数组（≤50、去重）。**不传 = 开放任务**（任意人点链接自动加入，无需权限）；**传 = 成员任务**（逐学员建任务，需任务发布权限） |
| `endTime` | 否 | 截止时间 `YYYY-MM-DD HH:mm`（东八区，须晚于当前）；不传默认 now+365 天 |
| `noticeConfig` | 否 | 通知三态见下表 |

**通知三态**：

| 传参 | 行为 |
|---|---|
| 不传 | 默认发 1 条飞书「任务开始」通知（无需自己构造） |
| `[]`（空数组） | 明示不发（用户明确要求不发通知时用） |
| 配置数组 | 按配置发：`type`（1=任务开始 / 2=截止提醒）、`channel`（1=飞书 / 2=钉钉卡片 / 3=钉钉待办）、`title`/`content`/`advance_time`/`priority` |

**响应诊断字段**：`noticeDispatched`（bool）+ `noticeReason`（defaulted / opt_out / explicit / not_applicable）——向用户复述通知结果以这两个字段为权威，不要自行推断。

**错误码**：`40001` 参数无效（含 endTime 格式/过期）；`40301` 无任务发布权限，或 userIds 含非本组织/已离职用户——**两种含义都不要重试**（改参数无效，向用户报告）；`40401` 课程不存在；`41001` 课程已删除。

开放任务（不传 userIds）无需权限，行为与旧版一致；链接与二维码双交付规则见 ai-customer-design 的交付章节。
