# 建课 / 改课 / 查询工作流

## 操作状态与允许动作（权威规则）

> **核心规则：`update` 发送成功（秒返 taskId）就不要重复提交，无论结果是否确定。**
>
> 完整表格见 [SKILL.md](../SKILL.md)

**关键判断**：
- 字段发生变化 ≠ 满足用户要求（可能改错了）
- 字段没有变化 ≠ 失败（目标可能原本就已满足）
- 验收应检查**目标条件成立且无意外变更**，而不只是比较前后是否不同

## 建课前准备：想清楚三个核心问题

AI 客户课程的核心是构建双人对话模拟场景——练习者和一个 AI 角色进行实战演练，完成后获得评估反馈和改进建议。

建课前先明确：

1. **练什么场景**：具体的业务对话场景是什么？（如：向医生推荐某款药品、处理客户投诉）
2. **AI 扮演谁**：AI 在对话中应该是什么角色？（如：血液科医生、愤怒的客户）
3. **怎么评判**：用什么标准衡量对话表现？（如：话术专业度、需求挖掘能力）

如果用户提供的信息不足以回答以上问题，先尝试从对话历史、可用工具和知识库中推断；推断后仍无法明确，再向用户追问。

## 课程简报检查清单

建课前必须能用一句话说清"这门课为什么对练习者有价值"——说不清则信息不足，需追问用户。以下 6 要素尽量自行补全，用户提供了就用用户的：

| 要素 | 说明 |
|------|------|
| 课程场景 | 行业背景、客户画像、对话环境 |
| 角色设定 | 练习者和 AI 各自扮演谁 |
| 评估维度 | 本次训练重点评估哪些方面 |
| 对话流程 | 大致阶段划分 |
| 专业知识 | 特定商品参数、卖点、竞品对比 |
| 参考资料 | 是否需要上传文档？**用户已提供原始文档文件时强制走文档上传路径**（见 [file-upload.md](file-upload.md)），不要提取内容转纯文字 |

补全后作为 `ai_customer.update` 的 message 传入。用户明确要求直接建课且信息充分时可跳过确认；否则先展示推断结果供用户确认。

## 建课工作流

建课主流程见 [SKILL.md §建课工作流](../SKILL.md#建课工作流)（唯一权威路径）。本节仅提供建课前的准备指引。

## 并发建课

- **并发上限 ≤3**：同时创建多门课程（>3）会导致服务端队列积压，后创建的课程可能等待 25+ 分钟
- 批量建课串行执行，或最多 3 门并行
- 某门课程长时间卡在 `create_status_prepare` 时，不要创建新课程，继续轮询等待

## 改课工作流（先记基线，后核实）

> ⚠️ **重试规则**：参考上方权威状态表。`update` 发送成功（秒返 taskId）就不重复提交，无论字段是否变化。

```text
Step 1: ai_customer.get → 记录当前各字段的实际值（基线）

Step 2: ai_customer.update → 发送修改诉求
  → 秒返 {"taskId":"xxx", "status":"running"}
  → ⚠️ 建课完成后 ~60s 冷却期内发改课 update 可能遇到 50003：
    等 60s 后重试，最多 3 次
  → 50002（agent 调用失败）→ 先用 `ai_customer.get` 验证内容是否已就绪（写库与状态翻转存在竞态），未就绪则等 ≥60s 改写消息重试 1 次，仍失败则报告

Step 3: ai_customer.update_status → 轮询直到 status="done" 或 "failed"
  → 每 5 秒一次

Step 4: ai_customer.get → 验证修改是否真的生效
  → ⚠️ AI 回复具有误导性：经常声称"配置已满足要求"/"已是目标值"但实际未修改。
    **只信 get 的字段值，不信 update 的 response 文字**
  → 首轮验证失败先等 30s 再查一次
  → 验证通过 → Step 5
  → 验证失败 → 重试 Step 2-3，最多 3 次，仍无变化 → 告知用户

Step 5: training.task.create_open_project → 生成新链接 → 双交付
```

**能力边界**：AI 助手能修改角色、阶段、评分等课程配置；**不能**改 roundLimit/timeLimit 等运行参数。

## 练习链接与二维码交付（缺一不可）

拿到 `training.task.create_open_project` 返回的 link 后，**必须在同一条回复中**同时完成两件事：

### ① 可复制的纯文本链接（必达项）

例如：`🔗 练习链接（可复制）：<链接>`。用户需要把链接转发给他人或粘贴到手机；纯文本链接也是二维码无法展示时的兜底。

### ② 二维码图片（必达项）

```bash
python3 <技能安装目录>/ai_customer_design/scripts/render_qr.py '<练习链接>' --out '<可写目录>/practice.png'
```

脚本成功后会打印 PNG 文件的**绝对路径**（不指定 `--out` 时默认写系统临时目录）。

**展示方式要按宿主能力自适应选择**（agent 自己支持哪种就用哪种）：

| 优先级 | 方式 | 适用宿主 |
|---|---|---|
| 1 | 文件读取并渲染 PNG 文件 | 支持图片渲染的宿主 |
| 2 | Markdown 图片语法（需使用可访问的图片地址） | 支持 markdown 图片渲染的 Web/IM |
| 3 | 富媒体卡片 / 附件 | 宿主提供富媒体附件能力 |
| 4 | 输出 PNG 绝对路径 + 文字说明 | 无图片渲染能力的宿主（兜底，**不可省略**） |

- 成功：按上表选择宿主支持的最佳方式展示
- 依赖不可用（E-HOST- 类错误码，非零退出并回显原始链接）：宿主无 Python 运行时——**直接向用户展示原始练习链接**，并说明二维码步骤失败
- 参数或输出目录问题（E-USER- 类错误码，非零退出）：修正后重跑一次

### 禁止做法

- ❌ 只输出链接文本、不渲染二维码图片
- ❌ 只生成二维码文件但不做任何形式的展示（用户必须能直接看到图片，或至少拿到图片路径）
- ❌ 大模型直接生成 ASCII/Unicode 二维码（极易出错）——必须用脚本渲染
- ❌ 链接/二维码生成后不展示，直接进入下一个任务
- ❌ 在无法渲染图片的宿主上仍只走文件读取路径而不下探兜底

QR 不可用时仍须将练习链接原文展示给用户，并如实报告二维码未能生成（属于交付不完整，需排查 Python 运行时或脚本问题）。
